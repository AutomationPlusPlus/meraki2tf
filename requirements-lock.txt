# Hash-pinned RUNTIME closure for reproducible worker installs:
#
#   pip install --require-hashes --only-binary=:all: -r requirements-lock.txt
#   pip install --no-deps .
#
# Every entry pins one exact version and carries the sha256 of *every*
# artifact PyPI published for it. Hash-checking mode still admits only
# that release, byte for byte; carrying the whole set is what Dependabot
# regenerates, so do not hand-trim entries back to a single artifact —
# the next bump would silently reintroduce the mismatch.
#
# --only-binary=:all: is part of the command, not a nicety: the
# published set includes each project's sdist, and without it a
# platform with no matching wheel would quietly build from source at
# install time instead of failing loudly.
#
# Profile: CPython 3.14 / linux-amd64 — the shipped container images
# (python:3.14-slim) and the reference scheduled-worker platform. The
# closure itself is interpreter-dependent (anyio, for one, pulls
# exceptiongroup and typing_extensions on the older Pythons this project
# still supports), so on another interpreter re-resolve rather than
# editing by hand:
#
#   python -m venv /tmp/lock && /tmp/lock/bin/pip install -r requirements.txt
#   /tmp/lock/bin/pip freeze          →  the versions below
#   https://pypi.org/pypi/<name>/<version>/json  →  .urls[].digests.sha256
#
# The closure is httpx-based: the SDK dropped aiohttp and requests in
# its 4.x line, so the whole aiohttp/urllib3 stack that earlier
# revisions of this file pinned is no longer installed. A version bump
# alone does not re-resolve this — check `pip freeze` against the
# entries below whenever the SDK's major moves.
#
# Rationale (CLAUDE.md / pyproject): an unattended worker rebuild
# mid-incident must not silently pull an untested or tampered SDK.
# Dev tooling is NOT pinned here — this file is only the runtime bill
# of materials; see requirements.txt for the dev environment.
